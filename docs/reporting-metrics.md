# Reporting metrics — M20.1 foundation

This document is the source of truth for the read-only reporting API introduced in M20.1. Responses include a period with startDate/endDate, UTC startAt/endAt, endExclusive=true, IANA timezone and snapshotAt.

## Common rules

- API paths are /api/v1/management/reports/*. Every data query requires an active admin or manager. Staff is denied before aggregate queries. Admins see active stores network-wide. Manager scope is recomputed from current user_stores joined to active stores; a supplied store ID is accepted only within that scope. Out-of-scope store and employee filters return not-found, avoiding an existence oracle.
- Events are stored and ordered in UTC. Period presets today, last_7_days, last_30_days, current_month, previous_month and custom use calendar dates in the requested timezone, default Europe/Chisinau. Boundaries are local midnight and SQL uses [startAt,endAt). Custom dates are inclusive and capped at 366 days. stores has no timezone column, so the API does not claim configured store timezone. Schedule rows retain their timezone, but inclusion uses persisted localDate against report local dates.
- Counts are nonnegative integers. Ratios are percentages from 0 to 100, rounded to two decimals. Ratios/averages with a zero denominator/no observations are null; counts are 0.
- Event metrics use the named event timestamp. Current-state metrics are snapshots at snapshotAt; a past period does not reconstruct prior status. Immutable versions/history are used where present.
- Employee counts, available quiz assignments, employee rows and knowledge denominators include active staff with an active membership in scope. Network employee counts deduplicate by users.id. Employee drilldown returns only ID, display name and aggregates—no email, phone, HR profile or credentials. Explicit store_id owns each event. Quiz attempts have no store ID: store-level attempt counts use current memberships, and a multi-store employee's attempt may appear for each assigned store. Do not sum store-level quiz counts into a network total. Store participation excludes quiz attempts because their store cannot be identified.
- Queries are parameterized, read-only and bounded to 366 calendar dates. Store and employee lists have stable ordering and page sizes up to 100. Empty authorized scopes return zero/empty results. No staff rankings or comparative scoreboards are exposed.

## Existing dashboard compatibility

Existing /api/v1/dashboard/* endpoints are unchanged. Their inputs are arbitrary UTC ISO instants (default approximately the preceding 30×24 hours); M20 uses named local-calendar periods. Dashboard activeEmployeeCount includes active non-admin users including managers, while M20 activeAssignedEmployeeCount counts active staff only and deduplicates network-wide. Dashboard uploadedPhotoCount counts photos.created_at rows; M20 submittedReportCount counts report first versions by submitted_at. These are different grains. Dashboard quiz KPIs remain submitted graded exam attempts and retain existing archived revision semantics; M20 explicitly splits exam/practice/survey and reports current assignment completion. No existing KPI has been silently redefined.

## Unsupported or excluded metrics

- Actual worked hours, attendance, lateness and schedule adherence: source schedules are planned only.
- A specific store attribution for quiz attempts: the source has no store_id. Store counts use current membership attribution; store participation excludes quiz attempts.
- Historical as-of reconstruction for task, photo, campaign, inspection, issue, request, schedule publication or membership status where no complete temporal snapshot exists.
- Issue resolution-time average: although transitions are retained, a simple create-to-resolve duration would misrepresent reopen cycles and legacy records.
- Employee productivity scores/rankings, comparative mobile scoreboards, or inference about unauthorized groups.
- Per-store timezone: stores has no timezone field; callers can choose a valid IANA timezone and Europe/Chisinau is the default.
- Notification/outbox delivery states are infrastructure telemetry, not business outcomes; retries can duplicate delivery attempts, and those records have no reliable store attribution.

## Query and performance policy

M20.1 adds parameterized PostgreSQL aggregate queries through Drizzle over existing source tables and indexes. It adds no migration, summary table, materialized view or external analytics system. Indexes/read models require representative EXPLAIN ANALYZE BUFFERS evidence and an identified bottleneck.

### Synthetic baseline (local PostgreSQL, 2026-10-31)

- Fixture: 12 synthetic stores, 120 active staff, 10,000 task occurrences distributed across 30 report days; selected store contained 834 occurrences. The scoped overview was exercised through the real Hono HTTP route.
- Scoped overview response: 15.60 ms and 11.16 ms in two consecutive full-suite runs (a separate targeted run measured 14.87 ms). The spread is local test-run/cache noise, not an SLO.
- Representative query: count task occurrences by store and the same 30-day half-open created_at interval. Both full-suite plans used Aggregate → Bitmap Heap Scan on task_occurrences → Bitmap Index Scan using task_occurrences_store_status_idx. The heap scan returned 834 rows. Planning was 0.063/0.070 ms; execution 0.549/1.033 ms; 254 shared hit blocks in both plans and zero shared read blocks.
- Decision: no index or summary table added. The existing store-leading index produced a fast scoped plan on this fixture; re-measure with production-scale cardinality and actual query concurrency before considering a store/date index. These results do not establish production latency.

### Integration and authorization evidence

- A fresh disposable PostgreSQL suite database was verified as database `vizaje_m203_suite`, user `vizaje_m203_suite`, bound only to `127.0.0.1:32769`; all repository migrations were applied. A separate disposable database was used for authenticated Admin/API HTTP and browser fixtures so suite tests could not observe unrelated acceptance records. Neither database was development or production data.
- The full API/PostgreSQL suite passed twice on the clean suite database: 86 tests, 0 failures, 702 assertions per run across 23 files. This includes report reconciliation, scope, empty/null behavior, allowed-store filters, pagination, DST/leap-date/custom-period validation, plus existing dashboard regression tests.
- The real HTTP scenario returned 200 for all ten Admin BFF reporting routes. Admin saw two active stores and two active staff; one-store and multi-store managers saw one and two authorized stores respectively. Cross-store and cross-employee filters returned 404, staff reporting returned 403, missing BFF session returned 401, invalid date returned 400, and authenticated responses were `private, no-store`.
- Chromium exercised all eight Admin views, URL-backed period/store filters, pagination, accessible chart data table, loading and 503 error states, Light/Dark, keyboard filter order, 1440×1024 and 768×1024 layouts, and manager scope. The tablet document had no horizontal overflow and no browser JavaScript errors. This is local browser acceptance, not production or device validation.

### Time and performance results

- Chisinau local dates use UTC half-open bounds. Tests cover a 23-hour spring DST day, a 25-hour autumn DST day, 2024-02-29, current/previous month, today, last 7/30 days, custom inclusive dates, and the 366-day maximum/rejection above it.
- The clean-database synthetic performance repeat used 12 stores, 120 active staff, 10,000 task occurrences over 30 days, and 834 occurrences in the selected store. Two scoped overview HTTP measurements were 13.81 ms and 16.83 ms. Both representative `EXPLAIN (ANALYZE, BUFFERS)` plans used Aggregate → Bitmap Heap Scan → Bitmap Index Scan on `task_occurrences_store_status_idx`; execution was 0.809 ms and 0.431 ms, with 0 shared read blocks. This two-run sample is not a stable percentile or production SLO; no index or summary table was added.

### Release status and limitations

M20.1–M20.3 passed local functional acceptance. No production deployment was performed. Before release, validate production HTTPS/session/cache settings, measure at production cardinality and concurrency, and configure operational monitoring. Existing documented limits remain: there is no historical as-of reconstruction without temporal source history; quiz store attribution follows current memberships and is non-additive; stores do not carry a timezone; and schedules represent planned hours only.
